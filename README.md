# 水电站机组运行检修管理平台

面向电站台账、机组运行、调速励磁、主变与闸门、大坝渗流位移监测、机组检修与发电计划的一体化水电站运行检修管理平台。

这是一个**纯前端**管理平台：Vue 3 + Vite + TypeScript，仓库里没有后端服务。业务数据由
`frontend/src/data/` 下的本地数据层提供：首次打开用示例数据播种，之后的登记、筛选与状态流转
结果都持久化在浏览器 `localStorage` 里，刷新或重开浏览器都还在。dev server 已关掉自动打开页面，
启动后按终端打印的地址手工打开。

## 目录结构

```text
.
├── frontend/                 Vue 3 + Vite + TypeScript 前端（唯一运行单元）
│   ├── src/views/            每个业务模块一个页面
│   ├── src/api/local-service.ts   本地数据服务：列表、筛选、动作流转、导出
│   ├── src/data/             模块元数据 / 示例数据 / localStorage 持久化
│   ├── src/stores/           会话与筛选状态
│   └── vite.config.ts        dev server 配置（open: false，无 /api 代理）
├── .gitignore
└── docker-compose.yml
```

## 启动

```bash
cd frontend
npm install
npm run dev
```

前端默认监听 `http://127.0.0.1:5173/`，dev server 不会自动打开浏览器，需要自己访问。

生产构建：

```bash
cd frontend
npm run build
```

## 约定

- 每个模块的页面在 `frontend/src/views/<模块>/index.vue`，页面只负责渲染，读写统一走
  `frontend/src/api/local-service.ts`。
- 字段、状态、动作与流转目标集中在 `frontend/src/data/modules.ts`；示例数据在
  `frontend/src/data/seed.ts`。
- 状态流转只允许在 `local-service.ts` 里改，页面组件不做业务判断。
- 想回到初始数据：清掉浏览器里 `hydropower-plant-om:entries` 这一项，或调用 `resetModule(模块)`。

## 主变压器「试验 → 告警 → 投运」链路

主变链路是真正落库的一条业务记录，代码在 `frontend/src/data/chain/`，独立于通用台账存储键
`hydropower-plant-om:transformer-chain:v1`：

- **试验结论一次落库**：在主变压器页「提交试验」后，试验结论、试验日期、试验人、读数与越限项
  一次写进主变台账；刷新页面或从其他入口进入读到的是同一份，不会退回「待试验」。
- **按试验时间覆盖（选定做法：覆盖，不追加）**：同一台主变只保留试验时间最新的一条结论，
  重复提交以新试验日期覆盖旧记录，不叠加；早于既有结论日期的提交会被拒绝，防止旧报告冲掉新结论。
- **告警决定能不能投运**：油温（≥85℃）或瓦斯保护（非正常投入）仍越限时，既不允许撤销告警，
  也不允许改为「运行中」；顺序必须是消除缺陷 → 复测合格 → 撤销告警 → 投运。
- **告警只追加、撤销留痕**：撤销不是删除，告警记录状态改为「已撤销」并记下撤销时间、撤销人、
  撤销原因；未解除的告警不允许重复发布。
- **可用容量两处对齐**：主变状态实时回写发电计划每一行的「可用主变台数 / 可用容量MVA」，
  主变页与发电计划页读到的台数始终相同，不会一边投运一边还算停运。
- **备品备件待办**：试验结论不合格自动落入备品备件页的待办清单（与主变页同源同一份）；
  复测合格时该待办自动闭环，也可手工闭环，闭环同样留痕。
- **存量迁移**：首次打开自动把通用台账迁入链路库——
  - 原有主变 id、变压器编号与既有试验结论原样保留，不重排、不被新版覆盖；
  - 存量试验按「试验日期」回填；早期只有纸质报告、没有试验人的，试验人统一补
    「纸质报告（未署名）」，并在「结论来源」标注「纸质报告回填（试验人缺项）」；
  - 迁移时仍处于「告警」的主变补建一条「未解除」告警，发布时间/发布人缺项按状态回补并标注；
  - 待办清单按登记时间升序迁移（缺登记时间的排末尾并标注「按迁移时间登记」），
    主变不合格结论与「待补充」备件合并编号；数字主键顺序分配，业务编号 `TODO-*` 保持稳定。
- **超时/断线**：提交走整库覆盖写（天然幂等），传输超时或断线时自动重试一次；
  重试仍失败会给出原因，且失败写入不会改动内存状态、不会产生半条记录。
- **导出**：主变台账、告警履历、待办清单三张 CSV 的列顺序与页面表格一致，并按页面相同过滤
  条件导出。

### 链路验证

```bash
cd frontend
npm run test:chain
```

用例（`frontend/scripts/`，用 esbuild 打包后在 Node 执行，非生产代码）覆盖：迁移回填与缺项标注、
刷新重读、按试验时间覆盖、告警撤销/投运门槛、撤销留痕、可用容量回写一致、待办闭环、
瞬时超时重试一次、持续失败给原因、导出与台账对齐。
